# 共享工段的产能瓶颈归因与改造试算

两套相邻装配线共享复验、缓冲与返工工位。本目录是一个只依赖 Python 3.11
标准库的决策工具：它先用记录反推现场规则并做历史重放校验，再把历史交付短缺
拆到材料、转移等待、检验返流三类原因，最后在同一批订单上比较增机、改检验
路由、加缓冲位，并给出资料不支持处的区间、分期起点和可回查的决策台账。

## 快速开始

```bash
python3 inspect_inputs.py                 # 资料规模
python3 inspect_inputs.py --rules         # 反推的节拍规则 + 重放校验
python3 inspect_inputs.py --options       # 方案可行性（预算/互斥组）
python3 -m unittest discover -s tests -v  # 全部检查

python3 -m planner.cli report             # 归因 + 对比 + 区间 + 重放
python3 -m planner.cli compare            # 只做方案对比（写入决策台账）
python3 -m planner.cli ranges             # 只做区间/稳健性分析
python3 -m planner.cli validate --shifts 0-2,19-21
python3 -m planner.cli phase2 --phase1 A --phase2 C
python3 -m planner.cli ledger             # 查看历史决策
```

## 现场规则（从记录反推，并由测试守住）

| 环节 | 规则 | 证据 |
|---|---|---|
| 装配 | `件数 + 5` 分钟，L1/L2 各 1 个并行位 | 132/132 单装配时长吻合 |
| 转移等待 | 按班次节拍 `3 / 7 / 11 / 15 / 19` 分钟（班次序号 mod 5） | 132/132 单等待吻合 |
| 首次复验 | `min(14, 2×件数)` 分钟，QA 1 个并行位 | 全部区间吻合 |
| 拒收返流 | 固定 2 件成组返工 18 分钟 → 等 2 分钟 → 复检 4 分钟 | 19 单全部吻合 |
| 放行 | 合格即交：`复验结束 + 2`；返工批 `复检结束 + 3` | 132/132 单交付时刻吻合 |
| 缓冲 | 按**批**占位（厚板 20 件/批、薄板 30 件/批），基线 3 批 | 历史最大占用 3 批 |

`planner.history.replay_check` 对 132 单逐单重放，四类检查（装配、等待、
返流、交付）全部零偏差。`planner.validate.replay` 再把历史班次送进**同一个**
前向模拟器：交付量、各班末积压位置、各工段占用分钟都对齐；唯一偏差来自记录
本身的 5 对 QA 区间重叠，模拟器按单台串行，因此可解释。

## 一、历史交付短缺的归因

对每单做反事实重放，把三类原因逐一消除：

- `M` 材料不足：装配只能等到实际到料；
- `T` 转移等待：含每班检验节拍，这是日历节拍而非设备排队（QA 历史占用约 16%）；
- `R` 复验返流：2 件返工 → 复检的整条尾巴，以及可分批先交的部分。

三因用**精确 Shapley**（2³ 个联盟）分摊，因此两线争夺同一台 QA 时不会把贡献
分别记满；交互项单独列出。可解释部分与结构性缺口相加恒等于总短缺，测试
`test_accounting_identity` 守住这个恒等式。

**结构性缺口**指即使三因全消除仍迟交的订单：它们的
`件数 + 5 装配 + min(14, 2×件数) 复验` 本身就超过承诺交期。增机不缩短单批
工时、加缓冲位也不缩短工时，因此这类订单只能靠改交期、拆批或改工艺解决。
报告按"最先撞线的工段"列出这部分，不算进 M/T/R。

**记录不全**单独处理：

- 22 单缺复验 `start_min`：只能由 `end − 时长` 反推，等待是上界，短缺给
  `[0, 记录值]` 区间；
- 5 对复验区间在同一台 QA 上重叠：两次读数不可能同时成立，涉及订单给区间并
  逐对列出重叠分钟；这些订单**不进入**精确比较，只报区间。

## 二、同一批订单上的方案比较

所有可行方案（预算 9,400 元、检验互斥组）跑**同一批 jobs、同一个情景读数**，
差异只来自方案本身。逐单给出：

- 哪些订单由迟交转为按期（收益可追溯到订单号）；
- 仍会卡住的订单，以及改由哪个工段接住（含等待分钟）；
- 只在组合时才受益的订单（单方案救不回、组合能救回）。

`B`（QA 加位）的施工窗口 10565–10685 正好压在已承诺 W1/W2 的交期上，因此
它在所有情景里都会让承诺订单迟交。工具把"承诺违约"当硬约束：这类方案即使
按期总量更高，也不作为推荐。

品类复验约束也显式校验：`A`（QA2）只能服务薄板，厚板路线没有替代复验站，
因此"为省成本改工艺"不能把厚板挪到 QA2。

## 三、资料不支持处只给范围

`planner.robustness` 在"返流集合 × 到料推迟 × 下达节奏 × 需求倍数"的每个
可行情景上重跑，给出每个方案的按期件/迟交量/缓冲阻塞区间。若区间互相重叠，
报告明确写"资料不支持唯一排序"，并列出能确定的事实与原因，而不是挑一个
精确解。资料本身的计划订单量相对班次能力很小（各工段占用 8%–16%），因此
在原始订单量下按期件无法区分方案——这一点报告会直接说明。

## 四、分期与决策台账

`phase2` 以一期**模拟出的期末状态**为起点：一期已交付的订单不再重跑，在制
订单带着剩余件数和最后所处工段进入二期，一期购入的工位作为既有资产进入
二期容量。台账（`out/decision-ledger.json`，只追加）记录每次评估所用情景
读数、可行方案集合、逐方案结果和内容摘要，可回查未选方案当时依据的需求与
约束。

## 目录

```
data/                 业务资料（只读）
planner/dataio.py     读取
planner/model.py      规则常量、批次换算、节拍
planner/history.py    逐单反推与重放校验、QA 重叠检测
planner/attribution.py 三因 Shapley 归因、结构性缺口、区间
planner/scenario.py   前向模拟器（分钟循环、固定派工顺序）
planner/validate.py   历史班次送模拟器、偏差分类
planner/compare.py    方案对比、逐单追溯、分期
planner/robustness.py 情景族区间与稳健性
planner/ledger.py     决策台账（追加、摘要、回查）
planner/report.py     文本报告
planner/cli.py        命令行入口
tests/                资料检查 + 行为测试
```
